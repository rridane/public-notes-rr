== RBAC (Role-Based Access Control) – Deep Dive

=== 🧩 Définition

RBAC est un **modèle de contrôle d'accès** qui repose sur les **rôles attribués aux utilisateurs** pour déterminer leurs **droits d'accès aux ressources** d’un système.

Un rôle est une **abstraction logique** regroupant des permissions. Un utilisateur hérite des permissions associées aux rôles qu’on lui attribue.

=== 🔐 Objectifs

* Minimiser les privilèges (principe du **least privilege**)
* Séparer les responsabilités (principe de **segregation of duties**)
* Simplifier l’administration des droits
* Auditer facilement les accès

=== ⚙️ Concepts clés

[cols="1,3",options="header"]
|===
| Élément | Description

| **Utilisateur** | Une personne, un service ou une entité identifiable dans le système
| **Rôle**       | Un ensemble de permissions représentatives d'une fonction métier (ex: `admin`, `comptable`, `lecteur`)
| **Permission** | Un droit d’exécuter une action sur une ressource (ex: `read:invoice`, `write:user`)
| **Session**    | Contexte d’accès où les rôles actifs de l’utilisateur sont définis (optionnel, utile dans RBAC avancé)
|===

=== 📐 Modèle standard (RBAC 96)

Le NIST a formalisé RBAC selon 4 niveaux :

. **RBAC0 (Flat)** : mapping direct utilisateur → rôle(s) → permissions
. **RBAC1 (Hiérarchique)** : permet des hiérarchies de rôles (ex: `admin > manager > user`)
. **RBAC2 (Contraintes)** : règles de séparation de tâches (ex: ne pas permettre `create_invoice` et `validate_invoice` à la même personne)
. **RBAC3 (Complet)** : combinaison de RBAC0 + RBAC1 + RBAC2

=== 📐 Modèle RBAC standardisé (NIST RBAC 96)

Le NIST a formalisé le contrôle d’accès basé sur les rôles en 4 niveaux successifs, chacun ajoutant des capacités au précédent :

==== 🧱 RBAC0 – Core RBAC (Modèle plat)

Le modèle le plus simple : une **association directe entre utilisateurs, rôles et permissions**.

* Pas de hiérarchie
* Pas de contrainte métier
* Parfait pour les petites applications ou les cas simples

[source,json]
----
{
  "roles": {
    "reader": ["read:article"],
    "editor": ["edit:article", "create:article"]
  },
  "users": {
    "alice": ["reader"],
    "bob": ["editor"]
  }
}
----

→ `alice` peut lire un article, `bob` peut créer/éditer un article. Les rôles n'ont aucun lien entre eux.

==== 🧱 RBAC1 – RBAC avec hiérarchie (Hierarchical RBAC)

On introduit une **relation d’héritage entre rôles**. Un rôle peut hériter des permissions d’un ou plusieurs autres.

* `editor` peut hériter de `reader`
* Les droits se propagent **de haut en bas** dans la hiérarchie

[source,json]
----
{
  "roleHierarchy": {
    "editor": ["reader"],
    "admin": ["editor"]
  },
  "roles": {
    "reader": ["read:article"],
    "editor": ["edit:article"],
    "admin":  ["delete:article"]
  },
  "users": {
    "alice": ["editor"]
  }
}
----

→ Grâce à la hiérarchie :
- `editor` = `edit:article` **+** `read:article` (hérité)
- `admin` = `delete:article` **+** tout ce qu’un `editor` peut faire

==== 🧱 RBAC2 – RBAC avec contraintes (Constrained RBAC)

Ce niveau ajoute des **règles de séparation de tâches** ou **incompatibilités entre rôles**.

* On interdit que certains rôles soient attribués simultanément à un même utilisateur
* Objectif : éviter les conflits d’intérêts ou les abus

.Exemple de contrainte : interdiction de combiner `create_invoice` et `validate_invoice`

[source,json]
----
{
  "roles": {
    "invoice_creator": ["create:invoice"],
    "invoice_validator": ["validate:invoice"]
  },
  "roleConstraints": [
    {
      "type": "mutually_exclusive",
      "roles": ["invoice_creator", "invoice_validator"]
    }
  ],
  "users": {
    "alice": ["invoice_creator"]
  }
}
----

→ Si `alice` est `invoice_creator`, elle **ne peut pas** se voir attribuer `invoice_validator`.

==== 🧱 RBAC3 – Unified Model (RBAC complet)

C’est la **combinaison des niveaux RBAC0 + RBAC1 + RBAC2** :

* Association utilisateurs ↔ rôles
* Hiérarchie de rôles
* Contraintes d’attribution
* Sessions d’activation de rôles (optionnel)

[source,json]
----
{
  "roleHierarchy": {
    "manager": ["employee"],
    "admin": ["manager"]
  },
  "roles": {
    "employee": ["view:report"],
    "manager": ["edit:report"],
    "admin": ["delete:report"]
  },
  "roleConstraints": [
    {
      "type": "mutually_exclusive",
      "roles": ["auditor", "finance_admin"]
    }
  ],
  "users": {
    "bob": ["manager"],
    "charlie": ["auditor"]
  }
}
----

→ `bob` peut :
- `edit:report` (via `manager`)
- `view:report` (hérité de `employee`)

→ `charlie` ne peut pas obtenir `finance_admin` si `auditor` lui est déjà attribué.

=== 🧩 Résumé

[cols="1,4",options="header"]
|===
| Niveau | Fonctionnalités

| RBAC0 | Attribution directe utilisateur → rôle → permissions
| RBAC1 | Rôles organisés en hiérarchie (rôle héritant d’autres rôles)
| RBAC2 | Contraintes sur l’attribution des rôles (mutuelle exclusion, cardinalité)
| RBAC3 | Modèle complet : RBAC0 + RBAC1 + RBAC2
|===


=== 🧱 Mise en œuvre dans différents systèmes

[cols="1,3",options="header"]
|===
| Système | Intégration RBAC

| **Linux** | `sudo`, `groups`, `selinux`, `polkit`
| **Kubernetes** | API `Role`, `ClusterRole`, `RoleBinding`, `ClusterRoleBinding`
| **PostgreSQL** | Rôles et privilèges via `GRANT`, `REVOKE`
| **Keycloak** | Rôles portés par les utilisateurs, mappés aux `scopes` ou `permissions`
| **OPA (Rego)** | Implémentation de RBAC via des règles explicites en Rego
| **AWS IAM** | Rôles IAM attribués aux utilisateurs ou services (équivalent RBAC étendu)
|===

=== 🔍 Détails Kubernetes RBAC

[source,yaml]
----
kind: Role
metadata:
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "watch", "list"]

kind: RoleBinding
metadata:
  name: read-pods
subjects:
- kind: User
  name: alice
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
----

=== 🔒 Bonnes pratiques

* ⚖️ **Équilibrer finesse et simplicité** : trop de rôles = explosion de la complexité
* 🔁 **Revue régulière des rôles** (audit, suppression des rôles orphelins)
* 🧩 **Rôles composites ou hiérarchiques** quand cela fait sens
* ❗ **Éviter les super-rôles** (`admin` omnipotents sauf cas exceptionnels)
* 📜 **Logguer les utilisations critiques** (accès sensibles, changements de rôle)

=== ⚠️ Limites du modèle

* Peu dynamique : ne prend pas en compte le contexte d’exécution (horaire, localisation, etc.)
* Ne gère pas facilement les cas complexes (ex: accessibilité basée sur un projet client spécifique)
* Risque de prolifération des rôles si la granularité est trop fine

=== 🧠 Vers des modèles hybrides

RBAC est souvent combiné à :

* **ABAC** : pour ajouter du contexte dynamique (`if user.department == resource.department`)
* **ReBAC** : pour modéliser les droits relationnels
* **OPA/Policies** : pour exprimer des règles complexes dans un moteur de décision dédié

=== 🧪 Tests & vérification

* 🧾 Jeux de tests formels (accès autorisé/interdit pour chaque rôle sur chaque ressource)
* 🔍 Audit régulier des affectations utilisateurs → rôles → permissions
* ✅ Intégration de la vérification RBAC dans la CI/CD (ex: tests de politiques dans OPA)

== ABAC (Attribute-Based Access Control) – Deep Dive

=== 🧩 Définition

ABAC est un **modèle de contrôle d'accès dynamique** basé sur l’évaluation de **conditions logiques** portant sur des *attributs*.

Au lieu d’associer directement des utilisateurs à des rôles ou des permissions, on évalue des règles comme :

[source]
----
IF user.department == resource.department AND action == "read"
THEN allow
----

=== 🔐 Objectifs

* Autorisation **fine-grain et contextuelle**
* Contrôle d’accès dynamique selon l’environnement d’exécution
* Réduction de la **prolifération des rôles**
* Flexibilité accrue pour les systèmes complexes ou multi-tenant

=== ⚙️ Concepts clés

[cols="1,3",options="header"]
|===
| Élément | Description

| **Utilisateur** | Porte des attributs (ex: `user.department`, `user.role`, `user.clearance`)
| **Ressource** | Porte aussi des attributs (ex: `resource.owner`, `resource.sensitivity`)
| **Action** | Ce que l’utilisateur tente de faire (`read`, `edit`, `delete`, …)
| **Environnement** | Contexte dynamique (heure, IP, lieu, MFA, etc.)
| **Politique (Policy)** | Règle logique conditionnant l'accès
|===

=== 🧠 Exemple de politique

[source,json]
----
{
  "if": {
    "and": [
      { "==": [ { "var": "user.department" }, { "var": "resource.department" } ] },
      { "==": [ { "var": "action" }, "read" ] }
    ]
  },
  "effect": "allow"
}
----

→ L’utilisateur peut lire la ressource **uniquement si** les départements correspondent.

=== 📦 Exemple complet

Supposons :
- Alice (département `finance`, clearance `high`)
- Ressource : rapport sensible (`department = finance`, `sensitivity = high`)
- Heure d'accès : 21h30

.Exemple de politique conditionnelle
[source,pseudo]
----
if user.department == resource.department
  and user.clearance >= resource.sensitivity
  and environment.time < 22h00
then allow
----

=== 🪪 Comparaison avec RBAC

[cols="1,2",options="header"]
|===
| RBAC | ABAC

| Contrôle par rôle assigné à l’utilisateur | Contrôle par attributs (user, resource, contexte)
| Plus simple, statique | Plus flexible, dynamique
| Risque de multiplication des rôles | Risque de complexité des règles
| Facile à auditer | Plus difficile à tracer/auditer
|===

=== 🧱 Mise en œuvre concrète

[cols="1,3",options="header"]
|===
| Système | Intégration ABAC

| **Keycloak** | Module `Authorization Services` : policies basées sur attributs utilisateur, ressource ou contexte (ex: JavaScript Policy)
| **OPA (Open Policy Agent)** | Évaluation d’attributs dans les règles Rego (`input.user.department == input.resource.department`)
| **AWS IAM** | Politiques conditionnelles via `Condition` (`aws:username`, `aws:SourceIp`, `aws:RequestTag`)
| **Auth0** | ABAC via Rules/Hooks ou Authorization Extension
| **XACML** | Langage XML standardisé pour policies complexes (via Axiomatics, WSO2, etc.)
| **Cedar (AWS)** | DSL moderne pour politiques ABAC (utilisé dans Amazon Verified Permissions)
|===

=== 🧩 Focus : ABAC avec Keycloak

Keycloak permet une implémentation ABAC complète via :

* **User Attribute Policies** → contrôle sur `user.attributes`
* **JavaScript Policies** → logique fine (`user.attributes["region"] === resource.attributes["region"]`)
* **Group Policies** → si les attributs sont encodés dans les groupes
* **Context Policies** → contexte d'exécution injecté via API (ex: heure, IP…)

.Exemple de JavaScript Policy
[source,javascript]
----
user &&
resource &&
user.attributes["department"] === resource.attributes["owner_department"]
----

Cette politique autorise l’accès uniquement si le département de l’utilisateur correspond à celui de la ressource.

=== 🧩 Focus : ABAC avec OPA (Rego)

[source,rego]
----
allow {
  input.user.department == input.resource.department
  input.action == "read"
}
----

OPA peut aussi combiner des règles RBAC + ABAC + ReBAC dans un seul moteur, versionné, testé, intégré dans CI/CD.

=== ⚖️ Avantages

* 🎯 Contrôle très granulaire et contextualisé
* 🌍 Idéal pour des systèmes avec des règles métiers évolutives
* 🧠 Permet d’automatiser des décisions complexes (ex: RGPD, sécurité nationale)

=== ⚠️ Limites

* 📉 Complexité croissante avec le nombre de règles
* 🔎 Audits plus difficiles qu’un mapping RBAC simple
* 🧪 Nécessite des outils solides pour tester et valider les règles
* 📜 Pas toujours lisible pour des non-techniques

=== 🧪 Bonnes pratiques

* 🧩 Commencer par RBAC si possible, ajouter ABAC en complément
* 🧼 Centraliser les politiques (OPA, Keycloak, PDP)
* ✅ Valider et versionner les règles (tests unitaires)
* 📊 Monitorer les décisions d’autorisation (logs + metrics)
* 👥 Limiter les attributs utilisés pour éviter les dérives incontrôlables

=== 🧠 Cas d’usage typiques

- 🌐 Plateforme SaaS multi-tenant
- 🏛️ Systèmes gouvernementaux avec niveaux de classification
- 🏥 Santé (ex: accès si `user.specialty == patient.department`)
- 📂 Dossiers juridiques ou RH avec visibilité limitée au service concerné
- 🧾 Conformité réglementaire (ex: GDPR, HIPAA)

== ReBAC (Relationship-Based Access Control) – Deep Dive

=== 🧩 Définition

ReBAC est un modèle de contrôle d’accès fondé sur les **relations entre entités**. Il ne se base ni sur les rôles (RBAC), ni sur les attributs (ABAC), mais sur la **topologie des liens** dans le système.

.Exemples typiques :
- `user is owner of document`
- `user is friend of friend of photo.author`
- `user is member of team that manages project`

=== 🔐 Objectifs

* Modéliser des **relations métier complexes**
* Gérer des **permissions dynamiques** basées sur des graphes d'entités
* Offrir un modèle intuitif pour les environnements multi-utilisateurs (SaaS, réseaux sociaux…)

=== ⚙️ Concepts clés

[cols="1,3",options="header"]
|===
| Élément | Description

| **Objet** | Ressource sur laquelle un accès est demandé (ex: document, ticket, projet)
| **Sujet** | L’utilisateur ou agent faisant la requête
| **Relation** | Lien entre le sujet et l’objet (ou un autre intermédiaire)
| **Namespace** | Catégorie logique pour les relations (ex: `document`, `photo`, `project`)
| **Path** | Chemin de relation (ex: `viewer -> team -> document`)
|===

=== 📦 Exemple simple

Exprimé en ReBAC :

> Alice peut accéder au document **si elle est `owner` du document**

[source,json]
----
{
  "object": "document:123",
  "relation": "owner",
  "subject": "user:alice"
}
----

=== 🧠 Exemple avec relation indirecte

> Bob peut accéder à la tâche **s’il est `manager` du projet parent**

[source]
----
task:42
↳ parent_project = project:7
↳ project:7.manager = user:bob
----

→ La règle d'accès suit la relation `task → project → manager`.

=== 📐 Comparaison avec RBAC / ABAC

[cols="1,1,1,1",options="header"]
|===
| Critère | RBAC | ABAC | ReBAC

| Basé sur | Rôle | Attribut | Relation
| Flexibilité | Moyenne | Élevée | Très élevée (natif pour graphe)
| Expressivité | Limité | Complexe | Très naturelle en modèle relationnel
| Performance | Excellente | Bonne | Dépend du moteur de graphe
| Idéal pour | Entreprises, droits statiques | Multi-tenant / sécurité contextuelle | Réseaux sociaux, SaaS, docs collaboratifs
|===

=== 🧱 Outils & moteurs ReBAC

[cols="1,3",options="header"]
|===
| Outil | Description

| **Google Zanzibar** | Moteur ReBAC distribué utilisé pour gérer les accès à tous les services Google (Docs, Drive, Photos…) — non open-source mais très influent
| **Authzed** | Reproduction open-source du modèle Zanzibar, expose une API pour exprimer les relations et faire des requêtes d’accès
| **Oso** | DSL déclaratif avec support de ReBAC via un graphe d’objets
| **OPA (Rego)** | Possible d’implémenter du ReBAC en encodant les relations comme `input.relations["project:7"].manager = "user:bob"`
| **Cedar (AWS)** | Permet de décrire des policies basées sur des relations entre ressources et sujets
|===

=== 🔍 Extrait de policy Zanzibar-like (Authzed)

[source,text]
----
definition document {
  relation owner: user
  relation viewer: user | team
  permission read = owner + viewer
}
----

→ Cela signifie :
- un `user` est `owner` ou `viewer` d’un `document`
- un `team` peut aussi être `viewer` → nécessite une autre relation entre user et team

=== 🧠 Cas d’usage typiques

* 🧑‍🤝‍🧑 Réseaux sociaux : qui peut voir un post ? un commentaire ?
* 🧠 SaaS collaboratif : accès par équipe, projet, rôle dans un projet
* 🏥 Santé : accès basé sur patient-assignation (médecin → dossier)
* 🏛️ Entreprises complexes : workflow conditionnés par hiérarchie et ownership

=== ⚖️ Avantages

* 🔗 Très naturel pour modéliser des droits liés à la structure des données
* 🧠 Approche déclarative orientée métier
* 💥 Très puissant dans les cas à graphe (multi-équipes, multi-projets)

=== ⚠️ Limites

* 💡 Modèle moins connu que RBAC/ABAC → courbe d’apprentissage
* 🔍 Debugging complexe (requiert visualisation du graphe relationnel)
* 🐌 Peut être coûteux si mal indexé (besoin moteur orienté graphe ou cache efficace)
* ❗ Nécessite souvent de repenser la structure des données et l’architecture d’accès

=== 🧪 Bonnes pratiques

* 📈 Indexer les relations pour des performances acceptables
* 🔍 Visualiser les chemins d’accès autorisé (outils type Authzed Playground)
* 🧼 Tenir une documentation claire des namespaces et relations
* ✅ Tester les politiques de bout en bout (qui peut accéder à quoi, par quel chemin)

== 🔁 Comparaison progressive entre RBAC, ABAC et ReBAC

Ce tableau présente trois cas concrets avec pour chacun les implémentations possibles selon les modèles de contrôle d’accès.

=== 🧪 Cas 1 – Gérable en RBAC / ABAC / ReBAC

_Un employé du département Finance peut consulter les rapports financiers._

==== 🔸 RBAC

[source,json]
----
{
  "roles": {
    "finance_reader": ["read:financial_reports"]
  },
  "users": {
    "alice": ["finance_reader"]
  }
}
----

→ On attribue manuellement le rôle `finance_reader` à Alice.

==== 🔸 ABAC

[source,json]
----
{
  "if": {
    "and": [
      { "==": [ { "var": "user.department" }, "finance" ] },
      { "==": [ { "var": "resource.type" }, "financial_report" ] },
      { "==": [ { "var": "action" }, "read" ] }
    ]
  },
  "effect": "allow"
}
----

→ Basé sur les attributs `user.department` et `resource.type`.

==== 🔸 ReBAC

[source,json]
----
{
  "document:42": {
    "viewer": ["group:finance"]
  },
  "group:finance": {
    "member": ["user:alice"]
  }
}
----

→ Alice peut lire le document car elle appartient au groupe `finance`.

=== 🧪 Cas 2 – RBAC atteint ses limites → ABAC / ReBAC requis

_Un employé peut modifier un document s’il est l’auteur OU s’il appartient au même département que l’auteur._

==== 🔸 RBAC ❌

Impossible sans créer un rôle spécifique par document ou combinaison auteur/département.

==== 🔸 ABAC ✅

[source,json]
----
{
  "if": {
    "or": [
      { "==": [ { "var": "user.id" }, { "var": "resource.author_id" } ] },
      { "==": [ { "var": "user.department" }, { "var": "resource.author_department" } ] }
    ]
  },
  "effect": "allow"
}
----

→ Très expressif, mais repose sur une structure d’attributs cohérente.

==== 🔸 ReBAC ✅

[source,text]
----
document:42
↳ relation: author = user:alice
↳ relation: visible_to = group:finance

user:bob ∈ group:finance
----

→ Bob peut modifier le document car il est dans le groupe lié à la ressource.

=== 🧪 Cas 3 – ABAC atteint ses limites → ReBAC seul possible

_Un utilisateur peut accéder à une tâche s’il est manager du projet parent de cette tâche._

==== 🔸 RBAC ❌

Aucune capacité de modéliser des dépendances dynamiques entre entités.

==== 🔸 ABAC ❌

Difficile sans dénormaliser les relations dans les attributs (non scalable).

==== 🔸 ReBAC ✅

[source,text]
----
task:42
↳ parent = project:7

project:7
↳ manager = user:alice
----

→ Alice peut accéder à `task:42` via la relation indirecte `manager of parent project`.

=== 🧠 Résumé synthétique

[cols="1,1,1,1",options="header"]
|===
| Cas | RBAC | ABAC | ReBAC

| Cas 1 – Accès simple (finance)     | ✅ | ✅ | ✅
| Cas 2 – Contexte utilisateur       | ❌ | ✅ | ✅
| Cas 3 – Relation indirecte (héritée) | ❌ | ❌ | ✅
|===


== Exemples - Histoire de Martin, responsable sécurité du Parc des Princes

=== RBAC

==== Succès de la mise en place

Martin entreprends de gérer rigoureusement les accréditations pendant les matchs, pour ce faire il commence par implémenter un système de gestion des droits RBAC.

Martin se réunit avec son équipe et commence par poser les permissions, essentiellement les zones ou peuvent avoir accès les individus :

----
zone_tribunes
zone_terrain
zone_vestiaire
zone_logistique
zone_loges_vip
full_zones
----

Conformément au pattern RBAC, Martin et son équipe dressent un ensemble de rôles et associent les permissions aux rôles :

----
"spectateur": ["zone_tribunes"],
"joueur": ["zone_terrain", "zone_vestiaires"],
"personnel": ["zone_logistique", "zone_coulisses"],
"securite": ["zone_tout"],
"vip": ["zone_tribunes", "zone_loges_vip"]
----

Chaque jour de match est assigné à chaque utilisateur, par son billet pour les spectateurs et par des badges pour les autres un ou plusieurs rôles:

----
{
  "roles": {
    "spectateur": ["zone_tribunes"],

Martin est satisfait, le jour de match, le personnel de sécurité n'a qu'à scanner le badge ou le ticket pour consulter les rôles et ainsi voir si la personne en question peut passer ou non.

==== Limite pour Martin et son équipe

Les matchs s'enchainent et tout fonctionne très bien, jusqu'à ce qu'un concours soit organisé, et qu'un spectateur tiré au sort ait gagné le droit d'accéder aux vestiaires. Cela revient à ajouter une permission à un spectateur. Deux solutions s'offrent alors à Martin et son équipe, ajouter un nouveau rôle, spectateur_avec_terrain comme ceci :

  "users": {

La même demande est faite pour des amis du président:

Puis un incident survient, le spectateur gagnant est surpris après le match sur le terrain, ce qui est strictement interdit, il n'était convié qu'au début du match. Martin est navré, les équipes de sécurité n'ont fait qu'appliquer les règles. Son modèle est défaillant.

Il envisage de créer des permissions plus fines comme:

----
zone_terrain_avant_match
zone_terrain_mi_temps
zone_terrain_apres_match
----

Mais une autre demande intervient l'interdiction d'accéder aux bancs, uniquement vers le rond central. Il faudrait créer:

zone_terrain_avant_match_full_terrain
...
----

Martin et son équipe se rendent compte que la finesse des droits impose maintenant un nouveau modèle, au risque d'avoir un système de gestion des rôles ingérable.

=== ABAC

Martin décide alors d'explorer un modèle basé sur des attributs (ABAC) pour répondre aux besoins suivants, que RBAC ne peut plus couvrir sans explosion combinatoire :

* Autoriser un spectateur à accéder au terrain uniquement avant le match, à l’occasion d’un concours.
* Permettre aux invités du président d’accéder à certaines zones sans avoir le rôle VIP.
* Restreindre l’accès au rond central du terrain à un moment précis (ex : coup d’envoi).
* Gérer les accréditations dynamiquement, sans redéfinir de nouveaux rôles pour chaque combinaison.

==== Succès de la mise en place

Martin pose alors les attributs nécessaires à la mise en place du nouveau système. Il tient à transférer tout le fonctionnement RBAC en ABAC.

===== ✅ Attributs utilisateur (`user`)

[cols="1,3",options="header"]
|===
| Attribut        | Description

| `user.type`     | Type d'utilisateur (ex: `spectateur`, `joueur`, `personnel`, `securite`, `vip`, `invité_president`)
| `user.badges`   | Liste de permissions exceptionnelles (ex: `terrain_avant_match`, `vestiaire_invite`)
| `user.id`       | Identifiant unique de l'utilisateur
| `user.nom`      | Nom de l'utilisateur (à des fins de journalisation ou d’affichage)
|===

===== ✅ Attributs de ressource (`zone`)

[cols="1,3",options="header"]
|===
| Attribut             | Description

| `zone.id`            | Identifiant unique de la zone (ex: `terrain`, `vestiaires`, `loges_vip`, `tribunes`)
| `zone.restrictions`  | Liste de restrictions spécifiques (ex: `rond_central_only`)
| `zone.access_times`  | Plages horaires valides pour l'accès à la zone
|===

===== ✅ Attributs de contexte (`env`)

[cols="1,3",options="header"]
|===
| Attribut          | Description

| `env.time`        | Heure actuelle (ex: `2025-07-31T20:30:00`)
| `env.match_phase` | Phase du match (ex: `avant_match`, `mi_temps`, `apres_match`)
| `env.event_type`  | Type d'événement (ex: `match`, `concert`, `spécial`)
|===

Il commence par restranscrire les anciennes règles sur ABAC :

==== 🔁 Règles ABAC consolidées

[source,rego]
----
# 🎫 Spectateur : accès aux tribunes
allow {
  user.type == "spectateur"
  zone.id == "tribunes"
}

# ⚽ Joueur : accès au terrain et aux vestiaires
allow {
  user.type == "joueur"
  zone.id in ["terrain", "vestiaires"]
}

# 🛠️ Personnel : accès aux zones techniques
allow {
  user.type == "personnel"
  zone.id in ["logistique", "coulisses"]
}

# 🔐 Sécurité : accès à toutes les zones standards
allow {
  user.type == "securite"
  zone.id in ["tribunes", "terrain", "vestiaires", "logistique", "coulisses", "loges_vip"]
}

# 👑 VIP : accès aux tribunes et loges VIP
allow {
  user.type == "vip"
  zone.id in ["tribunes", "loges_vip"]
}

# 🎁 Spectateur gagnant du concours : accès terrain uniquement avant le match
allow {
  user.type == "spectateur"
  "terrain_avant_match" in user.badges
  zone.id == "terrain"
  env.match_phase == "avant_match"
}

# 🛋️ Invité du président : accès aux loges VIP
allow {
  user.type == "invité_president"
  zone.id == "loges_vip"
}

# ⛔ Restriction sur le rond central du terrain (exclu si restreint)
allow {
  user.type == "joueur"
  zone.id == "terrain"
  not zone.restrictions[_] == "rond_central_only"
}

# 🌙 Sécurité de nuit : accès zone logistique uniquement en horaires nocturnes
allow {
  user.type == "securite"
  zone.id == "logistique"
  env.time >= "22:00"
  "nuit" in user.badges
}
----

Martin demande au service informatique d'implémenter la logique du côté des scanettes de sécurité. Le jour du match tout fonctionne parfaitement, tout est géré beaucoup plus finement. Le président félicite également Martin et son équipe, il constate que ses demandes son parfaitement gérées au cas par cas, et que ce n'est pas au détriment des règles plus basiques.

==== Incident majeur et désillusion

Un soir de match de gala au Parc des Princes, un incident éclate :
🚨 **Un invité, non identifié, est retrouvé dans le vestiaire de l’équipe adverse après le coup de sifflet final.** L’accès à cette zone est pourtant strictement réglementé, et la présence de cet individu provoque un scandale médiatique.

Le président exige une enquête immédiate. Martin lance donc un audit complet du système d'autorisation.

===== 🔍 Audit et révélations

Martin interroge l’outil d’autorisation ABAC et ses logs.
Il consulte tout d'abord les propriétés de l'utilisateur:

----
user.type = invite_president
user.badges = acces_event_special
user.id = 134566
user.name = doe
----

Martin consulte les règles pour les invite_president:

----
# 🛋️ Invité du président : accès aux loges VIP
allow {
  user.type == "invité_president"
  zone.id == "loges_vip"
}
----

[cols="1,3",options="header"]
|===
| Attribut             | Description

| `zone.id`            | Identifiant unique de la zone (ex: `terrain`, `vestiaires`, `loges_vip`, `tribunes`)
| `zone.restrictions`  | Liste de restrictions spécifiques (ex: `rond_central_only`)
| `zone.access_times`  | Plages horaires valides pour l'accès à la zone
|===

----
# 🛋️ Invité du président : accès au terrain (en dehors du terrain lui même) avant le match sur le banc
allow {
  user.type == "invité_president"
  zone.id == "terrain"
  zone.access_time = "avant_match"
  zone.restrictions = "banc"
}
----

----
# 🛋️ Invité du président : accès au terrain (en dehors du terrain lui même) avant le match autour du terrain
allow {
  user.type == "invité_president"
  zone.id == "terrain"
  zone.access_time = "avant_match"
  zone.restrictions = "tour_du_terrain"
}
----

Martin s'étonne pour commencer de ces deux règles ajoutées à 6 mois d'intervalle. Pour plus de propreté elles auraient du être rassemblées sous la forme suivante:

----
# 🛋️ Invité du président : accès au terrain (en dehors du terrain lui même) avant le match
allow {
  user.type == "invité_president"
  zone.id == "terrain"
  zone.access_time = "avant_match"
  zone.restrictions in ["tour_du_terrain", "banc"]
}
----

Il constate par ailleurs que le nombre de règles est très grand, et multiplie les cas ou les regroupements devraient être faits. Cela n'explique cependant par le souci.

Il continue son investigation sur le badge **access_event_special**. La première chose qu'il constate est que le nom de ce badge n'est pas très parlant.

Martin cherche toutes les règles contenant le badge `access_event_special`.

Il tombe sur la règle suivante, visiblement ancienne, écrite à l’occasion d’un match caritatif :

[source,rego]
----
# 🎟️ Invités spéciaux lors d’événements spéciaux : accès showroom, dont l'objectif est de tout faire visiter
allow {
  "access_event_special" in user.badges
  zone.restrictions[_] == "showroom_access"
}
----

En croisant cela avec la base de données des zones, il réalise que plusieurs zones — dont les **vestiaires visiteurs** — avaient été temporairement marquées avec `showroom_access` pour permettre à certains partenaires d’y faire un tour **avant le match**, sous escorte.

Pour rappel, chaque zone peut être flagguée d'une ou plusieurs restrictions, voici la tableau des attributs de zone :

[cols="1,3",options="header"]
|===
| Attribut             | Description

| `zone.id`            | Identifiant unique de la zone (ex: `terrain`, `vestiaires`, `loges_vip`, `tribunes`)
| `zone.restrictions`  | Liste de restrictions spécifiques (ex: `rond_central_only`)
| `zone.access_times`  | Plages horaires valides pour l'accès à la zone
|===

Mais cette restriction temporelle **n’est pas exprimée dans la règle.**

Résultat :
- Le badge est encore actif.
- La règle est toujours en place.
- La restriction temporelle est oubliée.

==> La règle autorise **tous les porteurs du badge `access_event_special` à accéder à toutes les zones marquées `showroom_access`… à n’importe quel moment.**

Et ces zones ont été **mal étiquetées** ou **jamais nettoyées** après l’événement.

===== 🧨 Le vrai problème : la logique contextuelle n’est pas dans les règles

Martin fait alors une découverte cruciale :
→ La logique métier est **externalisée dans les têtes** ou **dans les processus humains**, mais **pas formalisée dans les règles.**

Il interroge les équipes :
> « Qui devait avoir accès à ces vestiaires ? »
> « Pendant combien de temps ? »
> « Qui devait leur retirer l'accès après le match ? »

Aucune réponse claire.

→ Le système **ne capture pas l’intention d’origine**, seulement des permissions techniques.
→ **Les règles ne sont pas versionnées**, ni associées à des **scénarios métiers identifiables**.

===== 🌀 Accumulation de badges "événementiels"

Il constate en analysant l’historique que :
- 14 badges similaires à `access_event_special` ont été créés les 6 derniers mois.
- Ils ont des noms ambigus : `event_promo`, `vip_temp`, `loges_moment`, `terrain_sponsor`, etc.
- La logique d’expiration n’est jamais intégrée dans les règles → **pas de `env.time` ni `env.match_phase` dans la plupart des règles associées à ces badges.**

Résultat :
→ Le système est "trop souple", il autorise **par défaut jusqu’à révocation manuelle**, alors que beaucoup d’accès devraient être **temporaires et bornés**.

===== 📉 Conclusion du post-mortem

Martin documente ainsi la cause profonde :

[quote]
____
L’accès non autorisé était techniquement permis par une règle générique,
combinée à une zone mal étiquetée et un badge jamais révoqué.

Le système ABAC nous a donné la puissance et la flexibilité…
Mais sans gouvernance des règles, il est devenu une usine à gaz.
____

Il note les failles systémiques :
- 🔁 **Règles non factorisées**, provoquant de la duplication et des incohérences.
- 🧠 **Logique métier implicite**, jamais exprimée dans les règles.
- ⏳ **Absence de durée de validité explicite** sur les badges ou règles.
- 🔍 **Pas de traçabilité claire** entre un scénario métier et les règles correspondantes.

Martin comprend que son système a besoin d’un **modèle qui capture les relations humaines**, pas seulement des états d’attributs.

Il décide de passer au **modèle ReBAC**.


=== ReBAC – Le tournant relationnel de Martin

==== Constat

À la suite de l’audit de l’incident au vestiaire, Martin réalise que ni RBAC, ni ABAC seuls ne permettent de capturer **le lien réel entre les individus et les entités du système** :

- un spectateur n’a pas “le droit au terrain”, il a “été désigné gagnant d’un concours pour tel match”
- un invité n’a pas “le badge loge”, il a “été invité par le président à un événement donné”
- un photographe n’est pas “photographe_temporaire”, il est “assigné temporairement à une équipe”
- un agent de sécurité n’a pas “zone_nuit_logistique”, il est “agent_de_nuit sur zone_logistique”

Il faut **représenter la structure réelle des relations humaines et métiers.**

==== 🧠 Changement de paradigme

Martin introduit alors une **graph database** ou une **métamodélisation orientée relations** où :

- **les utilisateurs, zones, événements, rôles, personnes** sont des **nœuds** ;
- les **droits naissent des relations entre les nœuds**.

Il construit donc le graphe des relations :

[source,json]
----
{
  "relationships": [
    ["alice", "a_un_billet", "match_OL_PSG"],
    ["alice", "gagnant_du_concours", "match_OL_PSG"],
    ["bob", "joueur_de", "psg"],
    ["carol", "membre_de", "equipe_securite"],
    ["carol", "affecté_à", "zone_logistique"],
    ["carol", "travaille_pendant", "nuit"],
    ["david", "invité_par", "president"],
    ["david", "convié_à", "match_PSG_OM"],
    ["david", "a_un_acces_special", "loges_vip"]
  ]
}
----

Et il redéfinit les permissions par des **règles relationnelles** plutôt que des rôles :

==== 🔁 Traduction des anciennes règles RBAC/ABAC vers ReBAC

[source,rego]
----
# 🎫 Spectateur accédant aux tribunes
allow {
  zone.id == "tribunes"
  user == U
  [U, "a_un_billet", M]
  env.match_id == M
}

# ⚽ Joueur accédant au terrain et vestiaires
allow {
  user == U
  zone.id in ["terrain", "vestiaires"]
  [U, "joueur_de", E]
  [E, "participe_au", M]
  env.match_id == M
}

# 🔐 Membre de la sécurité accédant à toutes les zones
allow {
  user == U
  [U, "membre_de", "equipe_securite"]
}

# 🔐 Agent de nuit accédant à la logistique pendant la nuit
allow {
  user == U
  zone.id == "logistique"
  [U, "membre_de", "equipe_securite"]
  [U, "affecté_à", "zone_logistique"]
  [U, "travaille_pendant", "nuit"]
  env.time >= "22:00"
}

# 👑 VIP accédant aux loges VIP
allow {
  user == U
  zone.id == "loges_vip"
  [U, "a_un_acces_special", "loges_vip"]
}

# 🎁 Gagnant du concours accédant au terrain avant match
allow {
  user == U
  zone.id == "terrain"
  env.match_phase == "avant_match"
  [U, "gagnant_du_concours", M]
  env.match_id == M
}

# 🛋️ Invité du président accédant aux loges VIP
allow {
  user == U
  zone.id == "loges_vip"
  [U, "invité_par", "president"]
  [U, "convié_à", M]
  env.match_id == M
}

# 📷 Photographe temporaire assigné à une équipe
allow {
  user == U
  zone.id == "terrain"
  [U, "assigné_à", E]
  [E, "participe_au", M]
  env.match_id == M
  env.match_phase != "apres_match"
}
----

==== ✅ Avantages observés

Martin constate plusieurs améliorations :

- ✅ Chaque **événement** ou **contexte spécifique** est une entité à part entière (match, zone, équipe).
- ✅ Les **liens sont explicites** (gagnant_du_concours, affecté_à, convié_à).
- ✅ Les **autorisations sont inférées dynamiquement** à partir des relations, sans explosion de rôles ou badges.
- ✅ Une **timeline** peut être suivie : les relations peuvent être horodatées, et donc révoquées automatiquement.

==== 📅 Gestion temporelle des relations

Les relations peuvent porter des métadonnées :

[source,json]
----
["alice", "gagnant_du_concours", "match_OL_PSG", { "valid_from": "2025-07-30T18:00", "valid_until": "2025-07-31T20:00" }]
----

Et Martin enrichit ses règles :

[source,rego]
----
# Autorisation conditionnée à la validité temporelle
allow {
  [user, "gagnant_du_concours", M, meta]
  env.match_id == M
  env.time >= meta.valid_from
  env.time <= meta.valid_until
  zone.id == "terrain"
}
----

==== 🔐 Gouvernance : retour d’expérience

Martin établit les bonnes pratiques suivantes :

- Toutes les **autorisations sont désormais liées à une relation** ;
- Chaque **règle Rego est tracée à un scénario métier concret** ;
- Les **relations sont versionnées et auditables**, contrairement à de simples rôles ;
- Les **relations expirent automatiquement**, pas besoin de penser à révoquer manuellement ;
- Les **règles peuvent être lisibles par des non-techniciens**, via une modélisation en graphe.
